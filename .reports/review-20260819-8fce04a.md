## Findings

### 1. LOW — Dead props passed to `DialogSelect` (Confirmed)

- **File:** `src/tui.js` — `showScrollableUsage()` (~line 138) and `tableOptions` helper.
- **What:** The plugin passes `preserveSelection: true` as a `DialogSelect` prop, and `truncateTitle: false` / `titleWidth: 108` as option props.
- **Evidence:** Verified against `TuiDialogSelectProps` and its `Option` type in opencode v1.18.17 (`packages/tui/src/ui/dialog-select.tsx`): supported props are `title, placeholder, options, flat, onMove, onFilter, onSelect, skipFilter, current`; option supports `title, value, description, footer, category, disabled, onSelect`. None of the three plugin props exist. Solid ignores unknown props, so there is no runtime effect.
- **Impact:** None at runtime; misleading dead code that suggests behavior (selection preservation, title truncation control) that does not actually happen.
- **Fix direction:** Remove the three props, or gate them behind a feature check if they target a future opencode version.

### 2. LOW — Validation mismatch: `normalizePeriod` vs `parsePeriod` (Confirmed, probed)

- **File:** `src/stats.js:28-57` — `normalizePeriod()` / `parsePeriod()`.
- **What:** `normalizePeriod` validates only that the *amount* is a safe integer ≥ 1. `parsePeriod` then requires `amount * unitMs` (and derived values) to stay within `MAX_SAFE_INTEGER`. Large-but-safe-integer amounts pass normalization and fail parsing.
- **Evidence (Node v22.14.0 probe against `src/stats.js`):**
  - `normalizePeriod("104267282d")` → `"104267282d"` (accepted), then `parsePeriod` → throws `Invalid period: 104267282d`
  - `normalizePeriod("2562047788015h")` → accepted, `parsePeriod` → throws
  - `"6148914691236517205m"` → correctly rejected at `normalizePeriod` (amount itself unsafe)
- **Impact:** In the TUI, the period prompt (`shift+P`) accepts such input without warning — the warning path only catches `normalizePeriod` errors — and the next `render()` displays the raw `Invalid period: …` message as the dialog body. In the CLI, `npx opencode-skill-usage 104267282d` prints the error to stderr and exits 1. Not a crash; an inconsistent-validation UX wart for absurd inputs.
- **Fix direction:** Either cap the amount per unit inside `normalizePeriod` (e.g. reject when `amount * unitMs > MAX_SAFE_INTEGER`), or call `parsePeriod` as the acceptance check in the TUI/CLI input paths.

### 3. LOW — Session-agent cache LRU not refreshed on use (Confirmed)

- **File:** `src/server-core.js:83-99` (`chat.params` handler), ~line 135 (`tool.execute.after` lookup).
- **What:** `sessionAgents` is an LRU-style Map refreshed (`delete` + `set`) only in `chat.params`. The `tool.execute.after` handler does a plain `get()` without refreshing recency.
- **Impact:** A long-lived idle-then-active session can be evicted once 256+ newer sessions exist; subsequent skill uses in that session are logged with agent omitted → counted under `unknown` in the agent matrix. Minor telemetry fidelity loss in high-session-count environments only.
- **Fix direction:** Re-insert on `get()` in the skill-logging path (`map.set(id, map.get(id))` when present), making it a true LRU.

### 4. INFO — Day-granular retention; prune tied to skill events (Confirmed, by design)

- **File:** `src/server-core.js:22-48` (`pruneLogs`), `144-148` (prune scheduling).
- **What:** Files are pruned when `dayStart + DAY_MS <= cutoff`, so with `retentionDays: 30` a file can retain data ~31 days. Prune runs at most once per 24h and only as a side effect of a skill being recorded; with no skill usage, old files linger indefinitely.
- **Impact:** Cosmetic disk-usage drift; no correctness issue. Prune/read use the identical boundary expression, so writer and reader agree.
- **Fix direction (if desired):** Prune on `session.idle`/startup as well, or subtract `DAY_MS` from the cutoff.

### 5. INFO — `getRecords` swallows all read errors (Confirmed)

- **File:** `src/stats.js:97-102`.
- **What:** `readFile` failures are treated as "skip file" for *any* error, not just ENOENT (e.g. EACCES, EMFILE). Corrupt/partial lines are likewise skipped by `parseLine` filtering.
- **Impact:** Stats silently under-report when files are unreadable. Consistent with the plugin's telemetry-must-never-fail philosophy, but the stats side is user-facing, so silent data loss is worth at least a debug-level note or an aggregation of skipped files.
- **Fix direction:** Count skipped files/lines and expose in `--json` output or a stderr warning.

### 6. INFO — Leading-zero periods accepted (Confirmed)

- **File:** `src/stats.js` — `normalizePeriod`.
- **Evidence:** `normalizePeriod("007")` → `"7d"`; `parsePeriod` → valid ms.
- **Impact:** Harmless normalization quirk; arguably lenient-input behavior. No action needed.

### 7. INFO — `exports["./server"].config` purpose unverified

- **File:** `package.json` — `exports["./server"].config` block; asserted present by `test/plugin.test.js`.
- **What:** No evidence was found (in opencode v1.18.17 source) that opencode reads a package.json `config` block for plugin option defaults. The plugin's code-side defaults (`DEFAULT_RETENTION_DAYS`, etc.) make the block harmless either way; user-facing config via the opencode.json plugin tuple (`["skill-usage", { retentionDays: … }]`) is the documented, working path.
- **Status:** Unverified — reported as an observation, not a defect.

### 8. INFO — Test-suite maintainability gaps (Confirmed)

- **File:** `test/plugin.test.js`.
- **a)** `manifest.version === "0.7.3"` is asserted, so every release must touch the test (intentional tripwire or friction, maintainer's call).
- **b)** `src/cli.js` has no behavioral tests (only `node --check` syntax pass): argument parsing edge cases (`--json` after period, multiple args, error exit) are untested.
- **c)** No test for the #2 overflow disagreement between `normalizePeriod` and `parsePeriod`.
- **Fix direction:** Property/table-driven tests for `normalizePeriod`/`parsePeriod` agreement; a few CLI integration tests spawning the bin.

## Investigated and refuted (verified OK)

These were actively suspected during review and confirmed **not** to be bugs; recorded so future reviews don't re-chase them:

1. **State-path writer/reader mismatch** — refuted. `defaultOpenCodeStatePath()` mirrors opencode's `xdg-basedir` logic exactly (`XDG_STATE_HOME || ~/.local/state`, then `/opencode`, `/skill-usage`) on all platforms, including Windows (xdg-basedir has no Windows branch).
2. **`session.deleted` payload access** (`properties.info?.id ?? properties.sessionID`) — both shapes are correct per opencode v1.18.17 event publishers.
3. **Prune vs. read boundary inconsistency** — identical `dayStart + DAY_MS <= cutoff` expression on both sides; writer and reader agree.
4. **`"unknown"` column sort comparator inconsistency in `buildAgentMatrix`** — unreachable code path (single `unknown` key), no behavioral effect.
5. **`formatTable` with empty rows** — unreachable from actual callers (they return `""` / early message first).
6. **Concurrent multi-process appends to daily JSONL** — append-only lines via `appendFile`; interleaving risk acceptable for telemetry.
7. **CRLF line endings in log files** — `split(/\r?\n/)` and JSON.parse tolerate both.
8. **Keymap `registerLayer` disposer contract** — v1.18.17's `@opentui/keymap` returns a disposer function; plugin's usage is correct.
9. **`shift+P` period binding under `mode: "modal"`** — opencode's dialog implementation pushes `"modal"` onto the mode stack while a dialog is open, so the layer is active exactly while the usage dialog is shown, and the binding is disposed before the prompt replaces it. Design verified correct.
10. **Slash-command registration** (`slashName` + `namespace: "palette"`) — matches opencode's command/slash wiring; custom top-level fields on `Command` are allowed by its index signature.
